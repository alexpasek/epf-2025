# Our Work Project Review Checklist

Apply alongside [project rules](our-work-project-rules.md) and the [project brief](our-work-project-brief.md). Record pass, fail or not applicable with a short reason. Do not mark work complete merely because a checklist file exists.

## Evidence and authenticity — required before publication

- [ ] This is an actual EPF job with a confirmed city, work scope and delivered endpoint.
- [ ] Supplied photos belong to the job; permission for the intended publication is established.
- [ ] Every asserted neighbourhood, date, dimension, duration, material, finish level and customer statement has support.
- [ ] Optional unknowns are omitted; missing essentials keep the record in draft.
- [ ] No generated/stock image is presented as job evidence; no defects or results are digitally fabricated.
- [ ] Before/after pairs show the same area and correctly ordered stages, or the page avoids a before/after claim.
- [ ] A primed or unfinished endpoint is labelled accurately; work by other trades is distinguished.
- [ ] Private source references, permissions, personal details and precise residential location are absent from public payloads, assets and schema unless specifically authorized for publication.
- [ ] The job is not a duplicate of an existing record or a city-swapped version of another story.

## Useful content and local relevance

- [ ] Title/H1 and opening identify actual service, city and a useful job distinction.
- [ ] The story explains the original problem, actual work/decisions and delivered result using supported facts.
- [ ] Facts panel includes only known details; completion timing is distinct from publication dates.
- [ ] City/neighbourhood claims are consistent across page, cards, image captions and structured data.
- [ ] Real access/property/room/finish context is included when known, without fabricated local assumptions.
- [ ] Nearby placements retain the true city and are labelled accurately.
- [ ] No filler, city lists, keyword ribbons, invented landmarks or unsupported ratings/credentials are added for SEO.
- [ ] Photos/captions help explain the work; CTA asks for useful details about a similar project.
- [ ] There is enough substance for a standalone case study; otherwise retain a verified gallery item or draft.
- [ ] Optional FAQ contains useful visible questions only; no blog word-count or generated-image requirement has been imposed on the case study.

## Discovery and internal links

- [ ] The project uses one stable canonical URL under the agreed Our Work structure.
- [ ] Our Work lists the public project with a crawlable detail-page link.
- [ ] Matching city/service page links to the project, or a missing destination is documented and an accurate existing hub is used.
- [ ] The project links contextually to the main service, accurate local service and quote/contact page.
- [ ] Optional guide, neighbourhood and other project links are relevant and resolve correctly.
- [ ] Link targets use canonical public service URLs, not accidental advertising/noindex destinations.
- [ ] Cards/filter memberships come from the same record and accurately identify city/service.
- [ ] No empty city archives or indexable duplicate filter combinations are introduced.
- [ ] Coverage markers are not represented as completed-job markers.

## Metadata, imagery and technical checks

- [ ] One H1, logical headings, useful unique title/description and correct social image.
- [ ] Canonical resolves to the actual project URL; breadcrumbs match the visible hierarchy.
- [ ] Appropriate schema describes visible facts; EPF uses Organization authorship. No fictional business branch, project rich-result claim or review markup is added.
- [ ] Public canonical URL is in the sitemap; drafts/private evidence remain excluded.
- [ ] Real images use descriptive alt text, dimensions, responsive sources, sensible compression and correct loading priorities.
- [ ] Text/images/links are crawlable, not accessible only through a modal.
- [ ] Full project URL, trailing-slash behaviour, library card and local-service link work in the built site.
- [ ] Mobile and desktop layouts, image loading, before/after labels and usable controls are checked.
- [ ] Build and appropriate repository/image checks pass when implementation changes warrant them; unrelated workspace edits are preserved.
- [ ] Any unperformed check is reported explicitly instead of marked passed.

## Publication and handoff

- [ ] Follow deployment rules for any authorized publishing; do not deploy through the old Worker.
- [ ] Distinguish local implementation, live deployment and verified indexing in the report.
- [ ] Verify live URL, canonical, images and sitemap after deployment when deployment is in scope.
- [ ] Do not claim ranking gains, Maps placement, rich results or AI citations from these checks.
- [ ] Report files, project path/status, verified locality/service, intent, photos, local context, internal links, checks and unresolved items.

These checks guide future work. Creating these rule documents alone does not implement project routes, validators, publishing automation or a project database.
